================================================================================
1. 结论速览
================================================================================

一句话：Hunter 是一个「三进程 + App Zygote 预热 + 65 个 native 检测方法 + 25 MB
加密规则库」的重量级环境检测器，检测覆盖面在同类工具里属于第一梯队（root / 注入 /
hook / 调试 / 沙箱 / 虚拟定位 / 自动化脚本全覆盖）。

它的检测强，但工程上留了三个硬伤：

  ① 更新通道是 http 明文 + 硬编码 IP + 装包权限 —— 可以中间人下发 APK
  ② native 侧用 popen 执行 shell，PATH 一旦被污染，检测结果由攻击者决定
  ③ 65 个检测方法全部靠 RegisterNatives 动态注册，hook 一处即全盘失效

三条里 ① 是安全漏洞，② ③ 是检测可靠性缺陷（对「被测方」而言是最实用的绕过点）。


================================================================================
2. 应用结构：三进程 + App Zygote
================================================================================

从 AndroidManifest 还原的进程模型：

  +---------------------------+----------------------------+--------------------------------+
  | 进程                      | 组件                       | 属性                           |
  +---------------------------+----------------------------+--------------------------------+
  | :hunter_main_process      | com.zhenxi.hunter.App      | 主进程，UI 与 Java 层调度      |
  |                           |                            | zygotePreloadName=.HunterPreload|
  +---------------------------+----------------------------+--------------------------------+
  | :hunter_server_iso        | ZhenxiServer               | isolatedProcess=true           |
  |                           |                            | 独立 UID，无权限、无存储       |
  +---------------------------+----------------------------+--------------------------------+
  | :hunter_server_twin       | ZhenxiServerTwin           | useAppZygote=true              |
  |                           |                            | 由 App Zygote fork，预热载入   |
  +---------------------------+----------------------------+--------------------------------+

为什么要这么设计：

  - 隔离进程（isolatedProcess）拿不到应用权限，能测出「低权限下能否看到 root 痕迹」，
    这比带权限的自测更接近第三方风控的真实视角
  - App Zygote（useAppZygote + zygotePreloadName）在 fork 前就把 ClassLoader 和
    native 库装好，检测在 fork 之后的干净进程里跑，**常规的应用内 hook 打不到**
  - 三进程互相比对：主进程、隔离进程、twin 进程各自采集一份，结果不一致即视为异常
    （native 字符串里的 "check two error ,process name no match" 就是这条判据）

进程间通信用 AIDL：

      com.zhenxi.aidl.IZhenxServer
      com.zhenxi.hunter.ZhenxiServerIpc
      com.zhenxi.hunter.ZhenxiServerTwinIpc

两个 Server 组件都是 exported=false，外部应用直接 bind 不通。

3.1 Java 层检测入口
--------------------------------------------------------------------------------

核心类：com.zhenxi.hunter.NativeEngine（单类 65 个方法）

按用途分类（方法名即语义，作者没有混淆）：

  【root】
      checkRootFromAVCLog          读 logcat 的 "avc: denied" 判定 SELinux 拦截
      checkRiskFile                风险文件存在性
      getZhenxiInfoSH              Shell / su 相关

  【注入 / hook】
      getZhenxiInfoInjection       注入检测
      getZhenxiInfoMapELF          /proc/self/maps 里的可疑 ELF
      getZhenxiInfoNHIL            Native Hook 清单
      getZhenxiInfoOFLI / OFRL     打开文件 / 映射文件清单
      getZhenxiInfoMethodCode      方法体校验（比对 DEX 中的 code item）
      check_jvm_method(Method)     单个 Java 方法是否被 hook
      getZhenxiInfoMM              ART 方法入口点一致性

  【zygisk / zygote】
      checkZygisk
      checkFromZygote              从 Zygote 侧回看
      runInZygisk                  主动进 zygisk 环境采样

  【调试】
      DetectHardwareBreakpoints    ptrace 硬件断点扫描
      getZhenxiInfoCBinder         Binder 调用链检查

  【模拟器 / 改机 / 多开】
      getCPUFingerprinting         CPU 指纹（架构 + 核心数 + 特性）
      getZhenxiInfoEnv             运行环境
      getZhenxiInfoApkEnv          APK 运行环境
      check sandbox（native 侧）

  【网络 / 位置】
      CheckVpn                     VPN 检测
      getZhenxiLoctionCrc          定位数据 CRC（虚拟定位改机检测）

  【自保护】
      hideLinkerAndMaps            隐藏自身 so 在 linker 与 maps 中的痕迹
      getZhenxiInfoReleaseNative   释放/清理 native 资源
      getZhenxiInfoT / getZhenxiInfo9 等  清理与收尾

另外还有一个独立库：

      top.canyie.magiskkiller.SubprocessMain

  MagiskKiller 是社区熟知的 Magisk 检测库，特性是**起一个独立子进程**做检测，
  避免主进程被 hook 后检测失真。它和上面的 checkFromZygote 是同一个思路的两种实现。

Xposed 检测在 Java 侧另有一条线，字符串留有：

      antiXposed / antiXposed methodCache / antiXposed sHookedMethodCallbacks
      checkXposedMark get xposed mark class / check xposed mark in mem
      clean xposed hook item finish

即：主动去翻 XposedBridge 的 method hook 回调表，翻到即判 hook。

关键实现细节（从日志字符串还原）：

  · 反 hook 用 DobbyHook 给自身关键函数下 inline hook，先手自保护
  · 用 ptrace 起一个独立 tracer 线程（check ptrace thread start success !!!!）
    既能查别人有没有在跟踪自己，也能监控自身代码页是否被改
  · 用 UnwindStackPtrace 解调用栈，判定调用链是否来自异常模块
  · Check Linker Crc Error / find linker is hooked：校验 linker 代码段 CRC
  · find inconsistent dalvik-zygote-jit-code-cache：检查 JIT code cache 与
    Zygote 镜像是否一致，专门针对 FART / 脱壳类内存篡改
  · check apk sign path / inode / gid&uid：native 直接 fstat 自身 APK，
    比 Java 层 getPackageInfo 更抗 hook —— 重打包会在这里露馅

libhunter_maps_hide.so = 1,055,960 字节，函数名语义上就是「隐藏自己的 maps」，
与 Java 侧 hideLinkerAndMaps 配套：检测器先把自己藏干净，再去看别人的脏东西。

4. 检测链时序还原
================================================================================

  ① 用户点开 App
       ↓
  ② App Zygote 预热：HunterPreload 载入 ClassLoader 与 native 库
       ↓
  ③ fork 出 :hunter_server_twin（useAppZygote=true）
     —— 此时进程干净，常规应用内 hook 不在
       ↓
  ④ 主进程 :hunter_main_process 启动，MainActivity 拉起 UI
       ↓
  ⑤ native 初始化：JNI_OnLoad → DobbyHook 自保护 → 起 ptrace tracer 线程
       ↓
  ⑥ bindService 到 :hunter_server_iso（isolatedProcess，低权限）
       ↓
  ⑦ 三进程分别调 NativeEngine 的 65 个方法做采样
       ↓
  ⑧ 比对三份结果：
        - 结果不一致 → "check two error ,process name no match"
        - 任一进程命中   → 该项判定为异常
       ↓
  ⑨ 需要联网的项目（版本、Play Integrity、小米 SDK）单独走网络
       ↓
  ⑩ 汇总成 ListItemBean 列表 → 列表页展示 → 可导出/分享

  关键点：第 ③ 步是整个设计的核心。检测在 App Zygote fork 出来的进程里做，
          比在应用主进程里做难绕得多。绕它要么在 zygote preload 阶段动手，
          要么从 native 层（第 ⑤ 步之后、⑦ 步之前）介入。

5. 缺陷与绕过面
================================================================================

5.1 【高】明文 HTTP 更新通道，可下发任意 APK
--------------------------------------------------------------------------------

  证据链（三条，缺一不可）：

  (1) AndroidManifest 声明了装包权限
        android.permission.REQUEST_INSTALL_PACKAGES
        android.permission.INSTALL_PACKAGES
      并内嵌 XUpdate 框架（UpdateManager / DownloadService / UpdateFileProvider）

  (2) 更新地址是明文 HTTP + 硬编码 IP
        http://47.95.8.136:1111/update/checkVersion
      同段字符串紧邻着 "checkUpdateInline error" 与 "versionCode / appKey"

  (3) 网络安全配置全局放开明文
      res 混淆后的 r/3A.xml（AXML 解析结果）：
        <network-security-config>
            <base-config cleartextTrafficPermitted="true"/>
        </network-security-config>
      targetSdk=36 默认禁明文，是这份配置自己把它放开的。

  影响：
      同一网络下的攻击者（公共 Wi-Fi、ARP 欺骗、运营商劫持、DNS 投毒）
      可以伪造 checkVersion 响应，把版本号抬高，诱导 App 下载并安装攻击者的 APK。
      XUpdate 默认只比对版本号，**不对下载到的 APK 做签名比对**，
      装完就是完整权限接管（该 App 本身持有 READ_LOGS / QUERY_ALL_PACKAGES /
      INSTALL_PACKAGES / 摄像头 / 定位等敏感权限）。

      这条同时也污染检测结果：用了被投毒版本的检测器，结论不可信。

  修复方向：
      改 HTTPS + 证书绑定、对下载包做签名与 sha256 校验、把 base-config 收回去。

  复现思路：
      本机起 HTTP 服务，hosts 把 47.95.8.136 指向本机，返回抬高版本号的 JSON，
      观察 App 是否进入下载流程（观察点：DownloadService、UpdateFileProvider）。


5.2 【高】native 用 popen 调 shell，PATH 可劫持
--------------------------------------------------------------------------------

  证据：

      NativeEngine.popen(String): String
      NativeEngine.popen_list(String, String): ArrayList<String>
      native 字符串：cat /proc/self/maps、grep /libc.so、logcat -d -b main ...

           checkRootFromAVCLog 的实现依赖：
             logcat -d -b main -b system -b events -b kernel | grep 'avc: denied'

  问题：
      popen 走 execvp 语义，按 PATH 查找可执行文件。Android 上 shell 的 PATH
      通常包含 /system/bin、/system/xbin、/vendor/bin；部分定制 ROM、
      或 root 后挂载的目录会把 /data/local/tmp 一类可写目录带进 PATH。

      一旦被测环境能让 cat / grep / logcat 解析到攻击者放置的同名二进制，
      检测器执行的就是攻击者的代码 —— 它输出的 maps、AVC 日志、进程列表
      全由攻击者决定，检测结论直接反转。

  这是本条报告里**最实用的一条绕过面**，因为它不需要碰 App 本身，
  只需要污染被测设备的执行环境。

  观察点：
      在 /data/local/tmp 放一个同名脚本，比对 App 检测结果是否变化；
      或 hook execvp / popen 记录它请求了哪些外部命令。


5.3 【高】检测实现全部动态注册，单点失效
--------------------------------------------------------------------------------

  证据：

      只有 2 个 Java_ 前缀导出符号：
          Java_com_zhenxi_hunter_NativeEngine_getZhenxiInfoMethodCode
          Java_com_zhenxi_hunter_NativeEngine_getZhenxiInfoReleaseNative

      其余 63 个方法的实现全部通过 RegisterNatives 在 JNI_OnLoad 里动态绑定。

  含义（双向的）：

      对作者：动态注册让静态符号分析拿不到对应关系，增加逆向成本。
      对攻击者：**所有检测的入口收敛到一个函数注册表**。
               在 JNI_OnLoad 执行完之后 dump 这张表，
               或用 inline hook 把 63 个函数指针统一替换成「返回未发现」的桩，
               一次操作覆盖全部检测项。

      这也是为什么它要在 JNI_OnLoad 里立刻 DobbyHook 自己 —— 作者显然
      知道注册表是单点。但 DobbyHook 的初始化本身也是单点：
      挂在 JNI_OnLoad 之前（例如在 zygote preload 阶段），
      整套自保护就连同检测一起失效。

  对应防御建议：把注册拆散到多个 so、多个时机，关键项用独立进程 + 独立校验。


5.4 【中】导出组件与自定义 scheme
--------------------------------------------------------------------------------

  从 manifest 提取的导出面：

  +-----------------------------------------------+--------+---------------------------+
  | 组件                                          | 导出   | 说明                       |
  +-----------------------------------------------+--------+---------------------------+
  | com.zhenxi.hunter.MainActivity                | true   | singleTask，LAUNCHER      |
  | com.google.firebase.auth.internal.            | true   | scheme=recaptcha://       |
  |   RecaptchaActivity                           |        | host=firebase.auth        |
  | com.google.firebase.auth.internal.            | true   | scheme=genericidp://      |
  |   GenericIdpActivity                          |        | host=firebase.auth        |
  | androidx.profileinstaller.ProfileInstallReceiver | true | 受 DUMP 权限保护        |
  | com.google.android.gms.auth.api.signin.       | true   | 受自定义权限保护           |
  |   RevocationBoundService                      |        |                           |
  +-----------------------------------------------+--------+---------------------------+

  MainActivity exported=true 且 singleTask：任意应用可以直接拉起它，
  配合 task 复用可以做「检测结果截屏/覆盖」类钓鱼链
  （例如目标 App 里跳到 Hunter 的界面，用户以为在看检测结果）。

  Firebase 两个导出的 Activity 属 SDK 固有行为，风险有限，但
  recaptcha:// / genericidp:// 这两个 scheme 没有注册独占性校验，
  任何 App 都能抢注同名 scheme 做劫持，把用户引到钓鱼页。

  两者都不是致命洞，但配合「环境检测 App 常被用来验真」这个场景，
  社会工程价值不低。


5.5 【中】profileable shell=true 泄露内部
--------------------------------------------------------------------------------

  manifest 里：

      <profileable android:shell="true"/>
      android:largeHeap="true"

  Android 10+ 允许 shell 用 simpleperf / perfetto / heap dump 对
  profileable 应用做剖析。这意味着 adb 连着的情况下，
  可以从 shell 侧拿到方法调用采样、堆快照、native 调用栈，
  直接暴露 NativeEngine 的调用顺序与规则库加载点。

  对一个「自称检测环境」的工具来说，这是自己把内部结构摊开的做法。
  正常做法是用 debuggable=false 且不声明 profileable。


5.6 【中】规则库 ZipCrypto 加密，已知明文可破
--------------------------------------------------------------------------------

  证据（手工解析 assets/data.zip 的 local file header）：

      ver=20  flag=0x000b  method=8
      csize=1784026  usize=25427761  nlen=9  elen=28
      name = data.json
      dataStart = 67

      flag bit0 = 1 → ZipCrypto（传统 PKWARE 加密），不是 AES-256

  ZipCrypto 的问题：它是已知明文攻击的教科书案例。
  攻击者手上只要有 12 字节已知明文 + 对应密文，就能反推密钥流，
  然后用 bkcrack 一类工具还原整个 25 MB 的 data.json。

  data.json 大概率是「检测规则 + 白名单 + 特征库」，拿到就等于拿到
  完整的检测目录 —— 对分析者是天大的好事，对作者是规则泄露。

  而 12 字节已知明文极其好拿：JSON 文件开头几乎必然是
  {" 或 [\n{ 之类的固定前缀，配合 ZIP 里的明文校验字节（12 位）
  可以暴力验证。

  换个角度：这条不算「漏洞」，但它是本报告里**最有分析价值**的一条，
  因为 data.json 是整套检测的权威数据源。


5.7 【低】maps 自隐藏与 maps 检测自相矛盾
--------------------------------------------------------------------------------

  Java 侧有 hideLinkerAndMaps()，配套 libhunter_maps_hide.so（1.06 MB），
  作用是把自身 so 从 /proc/self/maps 与 linker 链表里藏掉。

  同时 native 侧又有 Check Maps Find Hide —— 检测别人的 maps 是否被人为隐藏。

  逻辑上成立，工程上是自证：它必须保证自己的隐藏方式对方检测不到，
  否则「我藏了」这件事本身就是异常特征。实际对抗中，
  隐藏 maps 的手法（改 linker 链表、抹 maps 内容、伪造 /proc 读取）
  本身会留下可观测副作用，例如：

      - linker 链表中缺失 so，但 /proc/self/map_files 里还在
      - maps 行数与实际映射数不一致
      - /proc/self/smaps 与 /proc/self/maps 对不上

  它自己的 Check Linker Crc Error 就是在防这类不一致，说明作者清楚这个软肋。


5.8 【低】单 IP 无备份、无证书绑定
--------------------------------------------------------------------------------

  更新服务只有一个 IP（47.95.8.136:1111），没有域名，没有备用节点。
  这个 IP 一挂或者一被墙，全部用户永远停在旧版本；
  同时因为没有域名，也就无从做证书绑定 —— 与 5.1 是同一个病根。
